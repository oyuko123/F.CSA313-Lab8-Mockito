## 4. Хэрэгжүүлсэн нэгжийн тестүүд

`CourseRegistrationServiceTest` класст нийт 8 тестийн арга бичсэн. Үүний A8 тест нь гурван өөр оролтын нөхцөлөөр параметрчилсэн байдлаар ажилладаг тул нийт 10 тестийн гүйцэтгэл үүссэн.

| Тест | Шалгах нөхцөл | Хүлээгдэж буй үр дүн |
|---|---|---|
| A1 | Идэвхтэй оюутан шаардлагатай хичээлүүдийг судалсан | `OK`, бүртгэл хадгалж, имэйл илгээнэ |
| A2 | Оюутан олдоогүй | `ERROR_NO_STUDENT` |
| A3 | Оюутан идэвхгүй | `ERROR_INACTIVE_STUDENT` |
| A4 | Урьдчилсан нөхцөл хангагдаагүй | `ERROR_PREREQUISITES` |
| A5 | Имэйл илгээх үед exception гарсан | Бүртгэл хадгалагдаж, `OK` буцаана |
| A6 | Оюутны ID эсвэл хичээлийн ID `null` | `IllegalArgumentException` |
| A7 | Имэйлийн агуулгад хичээлийн ID орсон эсэх | Агуулга `CS201`-г агуулна |
| A8 | Оюутан байхгүй, идэвхгүй, эсвэл хичээл байхгүй гэсэн 3 нөхцөл | Тохирох алдааны кодыг буцаана |

### Ашигласан Mockito аргууд

- `@Mock` — `StudentRepository` болон `EmailSender` хамаарлуудыг mock объект болгох.
- `when().thenReturn()` — mock объектын буцаах утгыг тохируулах.
- `verify()` — шаардлагатай метод дуудагдсан эсэхийг шалгах.
- `never()` — тухайн метод дуудагдаагүй эсэхийг шалгах.
- `verifyNoInteractions()` — тодорхой mock объекттой харилцан үйлчлэл үүсээгүй эсэхийг шалгах.
- `doThrow()` — имэйл илгээх үед exception үүсгэх.
- `ArgumentCaptor` — имэйл илгээхэд ашигласан body аргументыг барьж авч шалгах.
- `assertThrows()` болон `assertAll()` — exception болон хэд хэдэн шалгалтыг баталгаажуулах.
- `@ParameterizedTest` болон `@CsvSource` — олон оролтын нөхцөлийг нэг тестийн аргаар шалгах.

### `lenient()` ашигласан шалтгаан

A8 параметрчилсэн тестийн гурван нөхцөлд бүх mock тохиргоо ашиглагдахгүй байж болно. Жишээлбэл, оюутан олдоогүй үед хичээл байгаа эсэхийг шалгах алхамд хүрэхгүй. Mockito-ийн strict stubbing горимд ашиглагдаагүй тохиргоо нь unnecessary stubbing алдаа үүсгэж болзошгүй. Иймээс A8 тестийн хүрээнд ашиглагдахгүй байж болох тохиргоонуудад `lenient()` хэрэглэсэн. Энэ нь бусад тестүүдийн шалгалтыг бүхэлд нь сулруулахгүйгээр зөвхөн шаардлагатай тохиргоонд уян хатан хандах боломж олгосон.

## 6. Mutation testing

Mutation testing-ийн үед системийн эх кодод зориудаар жижиг өөрчлөлт хийж, тестүүд уг өөрчлөлтөөс үүссэн алдааг илрүүлж чадаж байгаа эсэхийг шалгасан. Туршилт бүрийн дараа эх кодын анхны нөхцөлийг сэргээсэн.

| Mutation | Зориудаар хийсэн өөрчлөлт | Тест | Алдаа | Exception | Үр дүн |
|---|---|---:|---:|---:|---|
| 1 | Идэвхгүй оюутны шалгалтыг хассан | 10 | 2 | 0 | `BUILD FAILURE` |
| 2 | Хичээл байгаа эсэхийн шалгалтыг хассан | 10 | 1 | 4 | `BUILD FAILURE` |
| 3 | Урьдчилсан нөхцөлийн шалгалтыг хассан | 10 | 1 | 0 | `BUILD FAILURE` |

Mutation testing-ийн лог файлууд:

- `results/mvn-test-mutant-1.txt`
- `results/mvn-test-mutant-2.txt`
- `results/mvn-test-mutant-3.txt`

Гурван өөрчлөлтийн үед бүгдэд нь тестүүд амжилтгүй болсон. Энэ нь тестийн багц тухайн бизнес логикийн өөрчлөлтийг илрүүлэх чадвартай байгааг харуулж байна.

Mutation testing дууссаны дараа эх кодын гурван шалгалтыг сэргээж, дараах командыг дахин ажиллуулсан:

```powershell
mvn clean test
```

Эцсийн үр дүн:

```text
Tests run: 10, Failures: 0, Errors: 0, Skipped: 0
BUILD SUCCESS
```

## 7. Дүгнэлт

Энэхүү лабораторийн ажлаар Mockito ашиглан `CourseRegistrationService` классын нэгжийн тестүүдийг хэрэгжүүллээ. Mock объект ашигласнаар өгөгдлийн сангийн үүрэгтэй repository болон имэйл илгээгчийн хамаарлыг тусгаарлан шалгах боломжтой болсон. JUnit 5-ийн assertion болон Mockito-ийн verification аргуудыг ашиглан амжилттай бүртгэл, алдааны нөхцөл, exception болон методын дуудалтуудыг баталгаажуулсан. Параметрчилсэн тестээр гурван өөр бүртгэлийн алдааг нэг тестийн арга ашиглан шалгасан. Анхны эх код дээр нийт 10 тестийн гүйцэтгэл амжилттай болсон. Mutation testing-ийн гурван хувилбар бүгд тестийн алдаа эсвэл exception үүсгэж, `BUILD FAILURE` үр дүн өгсөн. Иймээс хэрэгжүүлсэн тестүүд нь бүртгэлийн үндсэн логикийн зарим чухал өөрчлөлтийг илрүүлж чаддаг гэж дүгнэж байна.
